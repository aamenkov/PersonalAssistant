- Существующие настройки, команды и кнопки Telegram сохранены. Новый интерфейс, предпросмотр и обновление действий Telegram остаются за пределами задачи 029.

## Согласованные уточнения к этапам B и C

- Ежедневный слот идентифицируется сроком, локальной датой и типом. Изменение времени не меняет ключ. Критический слот дополнительно идентифицируется запланированным локальным временем, поэтому изменение интервала или начала окна не переименовывает общие слоты. В БД ключ также включает идентификатор платежа.
- Калькулятор использует интервал `[fromUtc, toUtc)` длиной до 366 дней. При переходе на летнее время отсутствующий ежедневный слот сдвигается на первую допустимую минуту этого же дня, отсутствующий критический слот пропускается. При повторе локального часа выбирается первое наступление времени.
- После простоя выбирается один актуальный слот. Обработанный новый слот не даёт права вернуться к более старому. У обычных напоминаний сохраняется отправка до конца текущего локального дня.
- Явно выбранная отсрочка допустима вне критического окна. Совпадение окончания отсрочки с обычным слотом даёт максимум одно сообщение, в том числе при нескольких экземплярах worker.
- До трёх попыток при подтверждённом временном отказе с учётом Telegram 429. Сетевые таймауты с неизвестным результатом не считаются подтверждённым отказом. Автоматического повтора для `Unknown` нет.

## 2. Исходное состояние

По результатам предварительного анализа:

- `ReminderBackgroundService` выполняет проверку примерно раз в минуту.
- `ReminderService` рассчитывает уведомления непосредственно при проверке.
- `User` хранит `ReminderDaysBefore`, `ReminderTimeLocal`, `TimeZoneId`.
- Предварительное уведомление отправляется за N дней.
- В день платежа отправляется отдельное уведомление.
- После просрочки уведомления отправляются ежедневно.
- Существуют отсрочки через час, вечером и завтра.
- Записи `Reminder` создаются до отправки Telegram-сообщения.
- Уникальность текущих уведомлений основана на платеже, сроке, локальной дате и типе.

При реализации обязательно сверить эти выводы с актуальным кодом.

## 3. Режимы уведомлений

### 3.1. Обычный

Поведение по умолчанию:

- Одно предварительное уведомление за N дней.
- Одно уведомление в день платежа.
- После просрочки — ежедневно утром до подтверждения оплаты.

Настраиваемые параметры:

- Количество дней до предварительного уведомления: 0–30.
- Время уведомления.
- Поведение после просрочки: не повторять или ежедневно.

При N = 0 предварительное уведомление отключается, но уведомление в день платежа сохраняется.

### 3.2. Настойчивый

Поведение по умолчанию:

- Начать за 3 дня до срока.
- Напоминать ежедневно в 09:00, включая день платежа.
- После просрочки — ежедневно утром до подтверждения оплаты.

Настраиваемые параметры:

- За сколько дней начинать: 1–30.
- Время ежедневного уведомления.
- Поведение после просрочки.

### 3.3. Критический

Поведение по умолчанию:

- Начать за 3 дня до срока.
- До последнего дня напоминать ежедневно в 09:00.
- В день платежа отправлять уведомления каждый час с 09:00 до 21:00 включительно.
- После просрочки — ежедневно в 09:00 до подтверждения оплаты.

Настраиваемые параметры:

- За сколько дней начинать: 1–30.
- Время ежедневного предварительного уведомления.
- Интервал в критический день: 1, 2 или 3 часа.
- Начало активного окна.
- Окончание активного окна.
- Поведение после просрочки: отключено, ежедневно или продолжать частые повторы.

Для частых повторов после просрочки использовать то же активное окно и интервал, что и в критический день.

Не отправлять уведомления вне активного окна.

При выборе частых повторов после просрочки предусмотреть ограничение количества отправок в сутки, соответствующее выбранному интервалу и окну.

Валидация должна запрещать некорректные окна и интервалы. В первой версии не поддерживать окна, переходящие через полночь.

## 4. Общие и индивидуальные настройки

У пользователя есть общий профиль уведомлений.

Каждый платёж:

- По умолчанию использует общий профиль.
- Может получить индивидуальный профиль.
- Может быть возвращён к общему профилю.
- Может иметь полностью отключённые уведомления.

Изменение общего профиля должно автоматически влиять на платежи без индивидуальных настроек.

Индивидуальный профиль хранит полный набор параметров, а не только отличия от общего.

Не копировать общий профиль в каждый платёж.

### Совместимость

## 6. Отправка и учёт уведомлений

Сохранить существующий `ReminderBackgroundService`.

### Исправить DI scope

Создавать отдельный scope на каждый проход worker.

Не удерживать scoped `DbContext` на протяжении жизни singleton `BackgroundService`.

### Исправить учёт доставки

Сейчас резервирование уведомления может ошибочно восприниматься как успешная отправка.

Разделить:

- Резервирование слота.
- Попытку отправки.
- Подтверждённую успешную отправку.
- Подтверждённую ошибку.
- Неопределённый результат.

Не считать резервирование успешной доставкой.

Не допускать, чтобы ошибка одного уведомления блокировала отправку остальных.

При подтверждённой временной ошибке предусмотреть повторную попытку с ограничением частоты. Учитывать `retry_after` при Telegram 429.

При неоднозначном результате отправки не выполнять бесконтрольные повторы: Telegram Bot API не предоставляет клиентский ключ идемпотентности для `sendMessage`.

Предложить минимальную политику обработки неопределённого результата и согласовать её до реализации.

### Проверка актуальности

Непосредственно перед отправкой повторно проверять:

- Платёж существует и активен.
- Срок оплаты не изменился.
- Платёж ещё не отмечен оплаченным за соответствующий период.
- Уведомления разрешены.
- Слот соответствует актуальному расписанию.
- Нет действующей отсрочки.

Уже принятые Telegram сообщения отозвать невозможно, но после подтверждения оплаты дальнейшие слоты старого периода не должны отправляться.

## 7. Отсрочка уведомлений

Сохранить существующую возможность «Напомнить позже».

Расширить варианты:

- Через 1 час.
- Через 3 часа.
- Сегодня до 19:00.
- Завтра в 09:00.
- Указать своё время.

Произвольное время вводится в локальном часовом поясе пользователя.

Если выбранное время сегодня уже прошло, не создавать отсрочку в прошлом. Предложить выбрать другое время или дату.

### Поведение

Допустим, критический режим отправляет уведомления каждый час.

В 14:00 пользователь выбирает «Отложить до 19:00».

Ожидается:

1. До 19:00 уведомления по этому платежу не отправляются.
2. В 19:00 приходит одно напоминание.
3. Пропущенные слоты не накапливаются.
4. После 19:00 возобновляется обычное расписание.
5. После подтверждения оплаты отсрочка отменяется.

Отсрочка действует только на конкретный платёж и конкретный платёжный период.

Если пользователь меняет отсрочку, новое значение заменяет старое атомарно.

Если момент окончания отсрочки совпадает с плановым уведомлением, отправляется только одно сообщение.

Не допускать ситуации, когда отсрочка создаёт дополнительный поток уведомлений параллельно основному расписанию.

## 8. Пропущенные уведомления и перезапуски

Если приложение не работало несколько часов:

- Не отправлять всю накопившуюся последовательность.
- Отправлять максимум одно актуальное уведомление по платежу.
- Не восстанавливать старые почасовые слоты пачкой.
- Далее продолжать расписание по обычным правилам.

При повторном запуске worker не должен отправлять уже обработанные слоты.

При изменении расписания будущие уведомления пересчитываются.

При изменении даты платежа слоты прежнего периода перестают быть актуальными.

## 10. Динамический предпросмотр

Предпросмотр должен показывать реальное расписание, рассчитанное по текущим выбранным параметрам.

Например:

```text
📅 Предпросмотр — VPS

17 декабря — 09:00
18 декабря — 09:00
19 декабря — 09:00
20 декабря — каждый час с 09:00 до 21:00
21 декабря — 09:00, если не оплачено
```

Требования:

- При изменении режима или любого параметра предпросмотр пересчитывается.
- Использовать `ReminderScheduleCalculator`.
- Использовать реальную дату следующего платежа.
- Учитывать часовой пояс пользователя.
- Для общих настроек использовать выбранный реальный платёж как пример, явно обозначив его.
- Если платежей нет, показывать параметры без календарных дат.
- Компактно группировать последовательные почасовые уведомления.
- Показывать не бесконечное расписание, а ближайшие события и правила повторов.
- Предпросмотр не должен создавать записи `Reminder`.
- Предпросмотр не должен отправлять сообщения.

**Важное UX-требование:** пользователь должен видеть результат изменения параметров без необходимости сохранять настройки и заново открывать экран.

Для этого допускается временное состояние редактирования. Изменения должны сохраняться в БД только после подтверждения пользователем.

Предусмотреть кнопки «Сохранить» и «Отмена».
