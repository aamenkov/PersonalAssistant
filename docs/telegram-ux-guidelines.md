# Telegram UX/UI Guidelines

## Назначение

Этот документ описывает presentation и UX conventions Telegram-ботов. Его можно переносить в другие проекты и адаптировать под конкретный продукт.

Документ не определяет бизнес-правила приложения. Domain и Application должны оставаться независимыми от Telegram UI.

**Business rule** описывает поведение предметной области:

- платеж имеет дату наступления;
- операция оплаты не должна создаваться дважды.

**Presentation rule** описывает способ показа этого поведения:

- пользователь видит «26 августа», а не `2026-08-26`;
- повторное нажатие кнопки показывает понятный результат, а не stack trace.

Главный принцип:

> Пользователь должен взаимодействовать со своей задачей, а не с внутренней моделью приложения.

## Термины

- **Reply Keyboard** — постоянная клавиатура внизу чата для перехода между основными разделами.
- **Inline Keyboard** — кнопки под конкретным сообщением для действий над его контекстом.
- **Card** — сообщение с одной сущностью и действиями над ней.
- **Screen** — логический экран бота: список, детали, редактирование, статистика.
- **Conversation step** — один шаг многошагового ввода.
- **Primary action** — главное частое действие текущего экрана.
- **Destructive action** — отключение, удаление или другое потенциально необратимое действие.
- **Empty state** — экран без данных с объяснением и следующим полезным шагом.
- **Power-user command** — slash-команда для совместимости или опытных пользователей, но не обязательная для обычного сценария.
- **Presentation helper** — централизованный formatter для денег, дат, расписаний или часовых поясов.

## Navigation Model

Reply Keyboard отвечает на вопрос:

> Куда пользователь хочет перейти?

Пример:

```text
💳 Ближайшие        📋 Все
➕ Добавить          📊 Статистика
⚙️ Настройки
```

Inline Keyboard отвечает на вопрос:

> Что сделать с тем, что сейчас показано?

Пример:

```text
[✅ Выполнено] [✏️ Изменить] [⋯]
```

Не смешивать глобальную навигацию и действия над конкретной сущностью в одной клавиатуре без веской причины.

Для Reply Keyboard:

- держать небольшое число основных разделов;
- предпочитать две кнопки в строке;
- не помещать туда действия с конкретным ID;
- не использовать слишком длинные подписи;
- оставлять primary action заметным.

Для Inline Keyboard:

- показывать 1–3 основных действия рядом с объектом;
- не перегружать строку;
- не ставить destructive action рядом с primary action без необходимости;
- текст кнопки должен описывать действие, а не внутренний статус.

## Message and Action Ownership

Связь объекта и действий должна быть визуально очевидной.

Плохо:

```text
Платеж A
Платеж B

[Изменить] [Удалить]
[Изменить] [Удалить]
```

Хорошо:

```text
Платеж A
[✏️ Изменить] [⋯]
```

```text
Платеж B
[✏️ Изменить] [⋯]
```

Предпочтительный паттерн для разумного количества объектов:

> one object → one message/card → one inline keyboard

Если используется общая клавиатура, имя объекта должно быть частью подписи каждой кнопки.

## Telegram Screen Model

Чат не является web-page, но логическая модель экранов помогает не превращать его в хаотичный поток сообщений:

```text
HOME
├── UPCOMING
├── LIST
│   └── DETAILS
│       ├── EDIT
│       └── MORE
├── CREATE
├── STATISTICS
└── SETTINGS
```

Разделяйте:

- top-level screen;
- details screen;
- edit screen;
- confirmation screen;
- conversation input step.

Reply Keyboard переключает top-level screens. Inline Keyboard работает внутри текущего screen.

Навигационное состояние не нужно переносить в Domain. `CurrentScreen` и `PreviousScreen` обычно являются Bot/Application concern.

## Edit vs Send New Message

Внутри одного логического экрана предпочтительно использовать:

- `EditMessageText`;
- `EditMessageReplyMarkup`.

Например, переход из карточки в More обычно должен изменить клавиатуру существующего сообщения, а не отправлять несколько новых сообщений.

Новое сообщение уместно, когда:

- появилась самостоятельная сущность;
- требуется пользовательский текстовый ввод;
- старое сообщение важно сохранить как событие истории;
- старое сообщение больше не отражает контекст;
- Telegram API не позволяет безопасно обновить исходное сообщение.

Не создавать десятки сообщений для простых callback-переходов.

## Back Navigation

`◀️ Назад` возвращает на предыдущий логический экран текущего inline-flow.

Пример:

```text
Список → Детали → Изменить → Сумма
Сумма → Изменить → Детали → Список
```

Не использовать глобальную Reply Keyboard как замену Back внутри сценария.

Каждая промежуточная клавиатура должна иметь понятный путь назад или отмены. Для опасного действия «Назад» не должен случайно означать подтверждение.

## Multi-step Conversations

Рекомендации:

- задавать один вопрос за раз;
- не спрашивать значение, которое приложение может надежно вычислить;
- не заставлять повторно подтверждать неизменяемые поля;
- сохранять ConversationState между шагами;
- не сбрасывать состояние при ошибке ввода;
- давать кнопку «Отмена»;
- после завершения показывать результат и следующий полезный шаг.

Плохо:

```text
Введите Interval
Введите Period
Введите NextPaymentDate
```

Хорошо:

```text
Название?
↓
Сумма?
↓
Как часто?
↓
Когда?
↓
Проверка
```

Текст ошибки должен объяснять ожидаемый формат:

```text
Не получилось распознать дату.
Введите, например: 26.09.2026
```

## Field-based Editing

Для существующей сущности предпочтителен паттерн:

```text
Что изменить?
[Название] [Сумма]
[Расписание] [Комментарий]
[◀️ Назад]
```

Пользователь выбирает поле, изменяет только его и возвращается на edit screen.

Не использовать последовательный сценарий с повторяющимся:

```text
Оставить текущее
Оставить текущее
Оставить текущее
```

для обычного редактирования. Отмена должна прерывать только текущий flow и возвращать в предыдущий контекст.

## Human-readable Formatting

Технические значения остаются в БД, API, callback data, логах и тестах. Пользователь должен видеть понятное представление.

### Dates

| Техническое | Пользовательское |
|---|---|
| `2026-08-26` | 26 августа |
| `2026-08-26` | 26 августа 2026 |
| дата относительно сегодня | сегодня / завтра / через 3 дня |

ISO-формат не показывать без необходимости. Для ручного ввода выбрать один пользовательский формат, например `ДД.ММ.ГГГГ`, и явно привести пример.

### Money

| Техническое | Пользовательское |
|---|---|
| `2000 RUB` | 2 000 ₽ |
| `20 USD` | 20 $ |
| `50 EUR` | 50 € |

Не складывать разные валюты без отдельной конвертации.

### Time zones

Хранить IANA identifier, например `Europe/Moscow`, но показывать:

```text
Москва · UTC+3
```

### Schedule

Вместо внутренних `Period = Monthly` и `Interval = 1` показывать:

- каждый месяц, 26 числа;
- каждые 2 недели;
- каждую неделю по пятницам;
- каждый год 15 сентября;
- разово 25 августа.

## Presentation Helpers

Форматирование следует централизовать в простых helpers, например:

- `MoneyFormatter`;
- `DateFormatter`;
- `TimeZoneFormatter`;
- `ScheduleFormatter`.

Не создавать интерфейс или отдельный слой для каждого formatter автоматически. Цель — убрать дублирование и сохранить единый стиль.

Presentation helper не должен менять бизнес-данные. Он получает DTO или значение и возвращает текст.

## Progressive Disclosure

Частые действия должны быть видны сразу. Редкие и опасные — скрыты глубже.

Сразу показывать:

- выполнить/оплатить;
- изменить;
- открыть детали.

Под `⋯` или на отдельном экране размещать:

- отключить;
- удалить;
- сбросить;
- административные действия.

## Confirmation Rules

Подтверждение нужно для:

- удаления;
- отключения важной сущности;
- необратимой операции;
- финансового действия, если риск ошибки оправдывает дополнительный шаг.

Не подтверждать отдельно:

- открытие экрана;
- смену месяца;
- безопасную навигацию;
- изменение только отображения.

Кнопки подтверждения должны описывать действие:

```text
[✅ Сохранить] [❌ Отмена]
[⏸ Отключить] [◀️ Назад]
```

Не оставлять без контекста одинаковые «Да» и «Нет».

## Empty States

Empty state должен содержать:

1. объяснение, почему список пуст;
2. полезный следующий шаг.

Плохо:

```text
Платежей нет.
```

Хорошо:

```text
Платежей пока нет.

Добавьте первый регулярный расход, чтобы получать напоминания.
[➕ Добавить платеж]
```

Для пустого ближайшего периода показать следующее событие, если оно известно.

## Loading and Errors

Пользовательское сообщение должно быть коротким:

```text
Не удалось сохранить изменение. Попробуйте еще раз.
```

Технические детали отправляются в `ILogger`, но не пользователю:

- stack trace;
- `DbUpdateException`;
- Npgsql details;
- database ID;
- токены и connection strings.

Ошибки временных Telegram/API операций должны быть безопасны для повторной попытки.

## Idempotent UI Actions

Callback может быть нажат несколько раз или доставлен повторно. Важные действия должны корректно обрабатывать повтор:

- не создавать вторую оплату;
- не удалять уже отключенный объект повторно;
- показать «Эта операция уже выполнена»;
- безопасно вернуть пользователя в актуальный экран.

UI-защита не заменяет бизнесовую идемпотентность и уникальные ограничения в хранилище.

## Callback Data Guidelines

Использовать компактный структурированный формат:

```text
entity:action:id
payment:view:123
payment:edit:123
stats:month:2026-08
```

Callback data должна:

- однозначно парситься;
- содержать только технически нужные данные;
- быть независимой от текста кнопки;
- создаваться централизованным helper-ом;
- проверять владельца объекта на сервере.

Не разбрасывать magic strings по обработчикам.

## Tone of Voice

Тексты должны быть:

- короткими;
- понятными;
- дружелюбными и нейтральными;
- без канцелярита;
- без лишних технических терминов;
- без чрезмерного количества emoji.

Плохо:

```text
Операция успешно завершена.
```

Лучше:

```text
Готово. Платеж сохранен.
```

Плохо:

```text
Укажите месяц в формате /stats YYYY-MM.
```

Лучше открыть текущий месяц и дать кнопки навигации.

## Emoji Guidelines

Emoji — смысловые маркеры, а не декорация. Рекомендуемые значения:

```text
✅ успех / оплачено
⚠️ предупреждение / просрочка
📅 дата
📊 статистика
⚙️ настройки
✏️ редактирование
🗑 удаление
➕ добавление
```

Один emoji должен сохранять одинаковый смысл во всем боте. Не добавлять emoji к каждой строке.

## Command vs UI

Slash-команды могут оставаться:

- shortcut для опытных пользователей;
- compatibility API;
- удобным способом диагностики.

Но основной пользовательский сценарий должен работать через кнопки. Не заставлять пользователя помнить `/stats 2026-08`, если текущий месяц и навигация доступны через UI.

Хорошие defaults:

- статистика — текущий локальный месяц;
- история — текущий локальный месяц;
- дата — сегодня или ближайшая допустимая;
- валюта — валюта профиля;
- timezone — настройка пользователя.

## Primary Action

Каждый экран должен иметь понятное основное действие:

- список платежей — открыть или оплатить платеж;
- детали — оплатить;
- редактирование — выбрать поле;
- создание — продолжить ввод;
- статистика — сменить месяц;
- пустой список — добавить первый объект.

Если primary action невозможно определить, экран, вероятно, перегружен.

## Destructive Actions

Отключение и удаление должны быть визуально отделены от обычных действий:

```text
⋯
↓
Отключить
Удалить
```

Перед окончательным действием объяснить последствия: сохраняется ли история, можно ли восстановить объект, затрагиваются ли другие данные.

## Telegram Limitations

При проектировании учитывать:

- ограничение размера callback data;
- ограничения Telegram на редактирование сообщений;
- старые inline-клавиатуры, остающиеся в истории чата;
- отсутствие полноценного web-style navigation stack;
- повторную доставку Update;
- необходимость отвечать на CallbackQuery;
- ограничения длины сообщения и количество кнопок.

Состояние, необходимое для восстановления диалога, хранить вне памяти процесса.

## Architecture Boundary

Telegram UI — presentation layer.

Не переносить в Domain:

- тексты сообщений;
- emoji;
- названия кнопок;
- callback data;
- текущий Telegram screen;
- историю навигации пользователя.

Не помещать бизнес-правила в formatter или Telegram handler. Сценарий обычно выглядит так:

```text
Telegram handler
→ Application use case
→ Domain rule
→ Repository
→ DTO
→ Presentation formatter
```

## UX Review Checklist

Перед завершением Telegram UX-задачи проверить:

- Reply Keyboard содержит только глобальные разделы;
- Inline Keyboard относится к конкретному контексту;
- связь объекта и кнопок очевидна;
- есть primary action;
- есть Back или Cancel для промежуточного flow;
- редактирование позволяет выбрать одно поле;
- технические значения скрыты;
- даты, деньги, расписания и timezone отформатированы единообразно;
- empty state предлагает следующий шаг;
- ошибки понятны пользователю и подробно логируются;
- повторный callback безопасен;
- slash-команды не обязательны для основного сценария;
- тексты и emoji выдержаны в едином стиле;
- UI-изменения не протекли в Domain;
- добавлены presentation/application tests.

## Перенос в другой проект

При копировании документа адаптировать только:

- названия основных разделов;
- доступные действия;
- валюты и локаль;
- поддерживаемые timezone;
- правила подтверждения;
- конкретные callback prefixes;
- команды и ограничения Telegram API.

Не копировать бизнесовые сущности и не использовать примеры как обязательную модель данных.
