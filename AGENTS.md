# Правила работы с проектом

- Каждая самостоятельная задача получает постоянный ID, отдельную ветку и временный корневой `TASK.md` только в этой активной ветке. Бизнесовые задачи используют `NNN`, технический долг — `TD-NNN`.
- В `master` не хранится активный `TASK.md`; для структуры используется `TASK.template.md`.
- Перед началом новой задачи проверить текущую ветку и убедиться, что рабочее дерево не содержит чужих незакоммиченных изменений.
- После завершения задачи сначала выполнить проверки, затем предложить пользователю создать коммит с кратким сообщением; не считать задачу сохраненной без коммита.
- После завершения задачи переместить `TASK.md` в `docs/tasks/<ID>-short-name.md`. Не создавать следующую задачу в той же ветке.
- `TODO.md` содержит только незавершенные задачи. После выполнения задачи удалить ее раздел из `TODO.md`; подробное ТЗ и итог сохранять в архиве `docs/tasks/`.
- Номера завершенных задач не переиспользовать и не перенумеровывать: `docs/tasks/` — исторический архив, а `TODO.md` — текущая очередь. Один и тот же ID используется в TODO, ветке, TASK.md и архиве.
- Если во время разработки или аудита найдена проблема, не маскировать ее в коде и не терять в переписке: добавить отдельный пункт `TD-NNN` в раздел технического долга `TODO.md`.
- Новую задачу начинать от актуального `origin/master`: создать новую ветку и новый корневой `TASK.md` на основе `TASK.template.md`.
- Перед предложением Pull Request обязательно проверить, что завершенная задача уже перенесена из `TASK.md` в `docs/tasks/`, корневого `TASK.md` больше нет, а архив содержит итог и проверки.
- Pull Request можно предлагать только после проверки архива задачи, отсутствия активного `TASK.md`, прохождения сборки/тестов и чистого `git status`.
- В конце каждой задачи сообщать статус ветки, коммита, тестов и наличие/отсутствие Git remote.
- Перед изменениями прочитать `TASK.md`, `REQUIREMENTS.md` и `ARCHITECTURE.md`.
- Сохранять название solution и проектов с префиксом `PersonalAssistant`.
- Не помещать секреты в исходный код, конфигурацию или логи.
- Не смешивать Telegram, EF Core и бизнес-правила в одном обработчике.
- После значимых изменений запускать `dotnet build`, `dotnet test` и относящиеся к задаче проверки.
- Не добавлять библиотеки и паттерны без необходимости.
- Обновлять документацию при изменении поведения или архитектуры.
- Невыполненные будущие функции записывать в `TODO.md`, а не оставлять мертвый код.

## Git workflow

Основная ветка — `master`. Рабочие ветки создаются от нее или от последнего принятого коммита и именуются с номером задачи:

```text
codex/001-project-foundation
codex/002-timezone-onboarding
codex/010-reminders
codex/TD-001-telegram-update-idempotency
```

Рекомендуемый цикл:

```bash
git switch master
git pull
git switch -c codex/<ID>-short-name
Copy-Item TASK.template.md TASK.md
# заполнить TASK.md под текущую задачу
dotnet build PersonalAssistant.sln
dotnet test PersonalAssistant.sln
git add .
git commit -m "Short task description"
```

Перед Pull Request выполнить финальный чек-лист:

```text
[ ] Все пункты текущей задачи выполнены.
[ ] Завершенная задача сохранена в docs/tasks/<ID>-short-name.md.
[ ] TASK.md перемещен в docs/tasks/<ID>-short-name.md.
[ ] В корне нет активного TASK.md.
[ ] README.md/ARCHITECTURE.md обновлены, если изменилось поведение.
[ ] dotnet build и dotnet test пройдены.
[ ] git status чистый после коммита.
[ ] Ветка опубликована и только после этого предложен Pull Request.
```

После локального коммита можно подключить удаленный репозиторий и отправить ветку через `git push -u origin <branch>`. Секреты, `.env` и реальные токены в Git не добавляются.
