# Правила работы с проектом

- Каждая самостоятельная задача получает номер, запись в `TASK.md` и отдельную ветку вида `codex/NNN-short-name`.
- Перед началом новой задачи проверить текущую ветку и убедиться, что рабочее дерево не содержит чужих незакоммиченных изменений.
- После завершения задачи сначала выполнить проверки, затем предложить пользователю создать коммит с кратким сообщением; не считать задачу сохраненной без коммита.
- После коммита завершенную задачу переносить в `docs/tasks/NNN-short-name.md`, а `TASK.md` обновлять под следующую задачу.
- В конце каждой задачи сообщать статус ветки, коммита, тестов и наличие/отсутствие Git remote.
- Перед изменениями прочитать `TASK.md`, `REQUIREMENTS.md` и `ARCHITECTURE.md`.
- Сохранять название solution и проектов с префиксом `TelegramAssistant`.
- Не помещать секреты в исходный код, конфигурацию или логи.
- Не смешивать Telegram, EF Core и бизнес-правила в одном обработчике.
- После значимых изменений запускать `dotnet build`, `dotnet test` и относящиеся к задаче проверки.
- Не добавлять библиотеки и паттерны без необходимости.
- Обновлять документацию при изменении поведения или архитектуры.
- Невыполненные будущие функции записывать в `TODO.md`, а не оставлять мертвый код.

## Git workflow

Основная ветка — `master`. Рабочие ветки создаются от нее или от последнего принятого коммита и именуются с номером задачи:

```text
codex/001-project-foundation
codex/002-timezone-onboarding
codex/003-payment-creation
```

Рекомендуемый цикл:

```bash
git switch master
git pull
git switch -c codex/NNN-short-name
dotnet build TelegramAssistant.sln
dotnet test TelegramAssistant.sln
git add .
git commit -m "Short task description"
```

После локального коммита можно подключить удаленный репозиторий и отправить ветку через `git push -u origin <branch>`. Секреты, `.env` и реальные токены в Git не добавляются.
